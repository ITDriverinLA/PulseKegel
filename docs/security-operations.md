# Security operations

## Required Replit Secrets

The analytics administration routes fail closed unless both of these secrets
are configured:

- `ANALYTICS_ADMIN_USERNAME`
- `ANALYTICS_ADMIN_PASSWORD`

Use a unique password generated by a password manager. Do not commit either
value to GitHub. After deployment, visiting `/analytics` opens the browser's
username-and-password prompt.

`INVALIDATE_CACHE_TOKEN` is also required for the sitemap cache-invalidation
endpoint. If it is absent, that endpoint returns `503` instead of accepting an
unauthenticated request.

## Analytics reset

The reset remains available to an authenticated administrator:

```sh
curl --user "ADMIN_USERNAME:ADMIN_PASSWORD" \
  --request DELETE https://pulsekegel.com/api/analytics/reset
```

The reset permanently deletes all analytics events. Confirm the target domain
and credentials before running it.

## Public endpoint limits

- Analytics ingestion accepts only the event types and fields used by the app,
  with a maximum of 20 events per request and 60 requests per IP per minute.
- Weekly AI reviews accept bounded, validated workout data. They are limited to
  10 requests per IP per hour and 250 requests globally per hour.

## Deploy schema

The Replit deployment build (`.replit`) runs `npm run expo:static:build` and
`node scripts/server-build.js`. It does not run `npm run db:push`.

On boot the server runs this idempotent migration for the PulseKegel 2.2.5
analytics columns (all nullable):

```sql
ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS device_model varchar(64);
ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS display_class varchar(16);
ALTER TABLE analytics_events ADD COLUMN IF NOT EXISTS window_width_bucket varchar(16);
```

If that migration cannot run, analytics inserts fall back to a legacy INSERT
that does not name those columns, so older app versions keep recording events.
A failed migration is logged and does not stop the process.

`npm run db:push` is still the step that applies the full Drizzle schema
(`shared/schema.ts`), including indexes and any table that is not created by
the startup statements above. Run it against the production database after
deploy whenever that schema changes (sync tables included). The startup ALTER
only adds these three analytics columns.

## Cloud sync (Epic G1 Path A)

Progress sync routes (`/api/sync/*`) require a Bearer token issued only after
the client has opted in and exchanged an Apple/Google identity token.

Configure (do not commit):

- `APPLE_CLIENT_ID` — Apple Sign-In client / Services ID
- `GOOGLE_CLIENT_ID` — Google OAuth web/Android client ID
- `SYNC_DEV_AUTH_SECRET` — optional lab-only; accepts proving tokens `dev:<secret>` or `dev:<secret>:<subject>` when client IDs are unset (never bare `dev:anything`)

Apple/Google identity tokens are verified with JWKS (signature, aud, iss, exp).
If client IDs are missing, `/api/sync/auth` returns `503` unless a proving
`SYNC_DEV_AUTH_SECRET` lab token is presented. Sync push/pull/delete always
require a valid session token — there is no anonymous progress upload path.

## App Store export compliance (`ITSAppUsesNonExemptEncryption`)

`app.json` sets `expo.ios.infoPlist.ITSAppUsesNonExemptEncryption` to `false` so
App Store Connect does not prompt Missing Compliance on every iOS upload.

Ashley confirmed (2026-09-19) that Path B **PKB2** local backup encryption
(PBKDF2-SHA256 + AES-256-GCM, user passphrase, on-device / AirDrop / Files only)
is covered by an applicable US export exemption for this product. The flag is
**not** a claim that the app uses only HTTPS/OS crypto — Path B uses AEAD for
optional local transfer backups. Revisit this Info.plist value if encryption
scope changes (e.g. new algorithms, server-side encryption of user content).
